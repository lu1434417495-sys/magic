④ 战斗运行时核心类图 问题最集中的区域

BattleRuntimeModule 是 service-locator hub：约 40 个服务全部字段内联 new()，再经 Xxx.Setup(this) 把 module 自己反向注入；服务间互访全部走 hub 的 internal 成员（如 GroundEffectService 经 _runtime._skill_orchestrator）。依赖不可声明、不可单测隔离。同一段 ~20 行接线代码在 module 内重复 3 次（L436 / L2120 / L2302）。

架构问题清单（按严重度）

P0 — 结构性

#问题证据
1无命名空间 / 无程序集边界：829 个类全局命名空间，分层纯靠目录约定，越层依赖编译期不可见全项目 namespace 声明数 = 0
2两个宽编排 hub：BattleRuntimeModule 与 GameRuntimeFacade 仍承担大量接线；历史行数已随 partial 拆分变化，不再用旧总行数作为 finding图 ③ ④
3战斗域体量失衡：battle 占全项目 51% 代码（143k 行），Top15 大文件中 11 个在 battle行数实测
4明确循环依赖：BattleDamageResolver ⇄ BattleEquipmentAbilityRuntimeService ✓ 已解 2026-07-20（IBattleEquipmentAbilityReactionService 接口，12 成员全覆盖；DTO 下移 core/）；剩余 ContingencySystem → module.ExecuteAutoCast → Orchestrator 回环图 ④ ⑥

P1 — 封装与边界

#问题证据
5internal 字段大开门 + 两阶段 Setup：模块内无封装，存在"未 Setup 即使用"时序风险（大量 _runtime?. 空值传播兜底）setup() 14 参
6越层反向边 6 处（图 ⑥，已修 2 余 4）：最严重为 PartyState → PendingCharacterReward 与 CombatEffectDef → BattleAttackRollModifierSpecplayer→systems 反向引用审计
7窗口管理与业务混合：RuntimeModalKind 已是 canonical 状态，字符串 modalId 是 UI 投影；仍需关注窗口上下文 Dictionary 长驻 facade 字段WorldMapSystem.RenderWindows
8字符串字典协议反复往返：typed → GDictionary → typed 在 world/settlement 层多次转换，是 handler 行数膨胀的机械来源CopyIfPresent 等

P2 — 体量与重复

#问题证据
9仍有超大单体文件：当前仅余 BattleUnitState(2797，需结构重构)；BattleMapPanel（→1213+5 partial）、BattleRuntimeModule（→2372+8 类）、BattleDamageResolver（→2199+4 文件）、BattleAiMutationGuard（→242+4 文件）、SettlementCommandHandler（→2833+4 类）2026-07-20 当前文件
10内容族模板膨胀：progression 105 文件 = 14 族 × 5–7 文件模板；equipment_abilities/ 49 文件中 42 个是 <200 字节空 partial 壳文件内容审计
11Def/Definition 边界本身有效：Resource authoring 与 immutable runtime definition 职责不同；只保留少量重复常量的维护债warehouse 域
12重复接线：Module 同一段 Setup ×3；WorldMapSpawnSystem 两处独立实例化（GameSession.cs:1486 / WorldMapDataContext.cs:654）行号实测
13宽接口 proxy 债务：WorldMapRuntimeProxy 有大量 pass-through，但也统一 command 执行、presentation delta 与 render，不再定性为纯转发调用链审计

P3 — 一致性风险

#问题证据
15诊断逻辑体量：BattleAiMutationGuard 约 3208 行常驻 ✓ 已拆分为 242 行守卫核心 + 快照模型/快照/屏障快照/投影 4 文件（2026-07-20，判定逻辑逐字未动）；是否迁出 production assembly 可单独立项方法审计
16utils 杂物抽屉：34 文件混杂 config / 日志 / lease / 52KB 渲染器；content 层 Builder 依赖 utils validator图 ⑥ 违规 6
17服务实例化不统一：工厂只覆盖 per-member 服务图，其余一半字段 new、一半方法内懒惰 newCharacterManagementModule
18序列化逻辑散布数据层：~15 个 State 类各自持有 ToDictionary/FromDictionary，save schema 变更需多点修改persistence 审计

架构亮点（应保持）

总体格局：基础设施层高度严谨，应用层（两个 god hub、超大 handler/service、无边界强制）仍在还历史债。
#亮点
1静态内容管线（图 ②）：单进程宿主、同步构建、seal 后只借用 frozen definition、borrower 审计 —— 全项目最干净的一条链
2分阶段 shutdown 管线：ApplicationLifetimeCoordinator 唯一 owner + lifecycle-correctness CI 门禁，legacy debt 归零要求
3战斗展示边界：BattleHudAdapter 只经 Facade 的 5 个只读入口取数，presentation 不触达 runtime 内部
4enemies 定义/执行分离：authoring Resource 不执行战斗行为，definition → assembler → evaluator 链路清晰
5plain C# 数据纪律：业务态 typed owner + Godot collection 仅边界投影，执行得相当一致
6测试资产：166k 行测试 / 278k 行产品（≈0.6:1），headless 文本命令 + 快照 lane 成熟
