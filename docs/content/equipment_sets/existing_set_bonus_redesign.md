# 既有 100 套传奇装备：套装效果重设计总则

> 状态：Content design / mixed landing。
>
> 本文与三份逐套设计文档定义新的套装效果方案。凤凰重生（Set 53）已经落地，当前实现真相见 [装备套装系统](../../design/progression/equipment_sets.md)；其余套装不得由本文推断为已经落地。
>
> 设计基线：2026-08-08 当前 checkout。旧的 [套装效果设计文档](set_bonus_design.md) 是机制与主题来源，不再是最终阈值权威。

## 1. 本轮边界

### 1.1 冻结：不改任何单品配置

以下内容继续以 23 份 `sets_*.md` 为准，本轮不得重写：

- 100 个套装的编号、各源文档现有名称、顺序与主题；既有护甲/饰品标题漂移也不在本轮静默改名；
- 1000 个成员的 `item_id`、槽位、`equipment_type_id`、tag、价格、获取叙述；
- 单件属性、描述、单件特殊效果及其触发条件；
- 每套固定 10 个既有成员，不增件、不删件、不换槽。

### 1.2 可重设计：套装奖励层

以下内容由本轮重新设计：

- 达成奖励的件数门槛；
- 各门槛的静态属性、被动、触发、主动能力、次数和持续时间；
- 旧 2/4/6 件效果在新成长链中的位置、强化方式与 typed owner；
- 同一效果跨门槛升级时的替换组、共享次数和状态生命周期。

旧文档中的标志性机制必须被吸收到新链路中；可以延后、拆分或升级，但不能因为当前 runtime 尚未支持就删除或改成无关的静态数值。

## 2. 不统一结构，但统一完成度

每套都必须满足两条底线：

1. **10 件都参与计数。** 不再出现设计了 10 件、奖励却在 4 件或 6 件提前结束的情况。
2. **10 件必有封顶效果。** 封顶必须完成该套玩法身份，不能只是把前一档数字再加一点。

中间门槛不采用单一模板。逐套设计可以从下列结构中选择，也可以在说明理由后使用等价变体：

| 结构族 | 常见门槛 | 适用玩法 | 设计节奏 |
|---|---|---|---|
| 稳步成形 | 2/4/6/8/10 | 武器连击、元素循环、通用战斗流派 | 每两件补齐一个环节 |
| 形态蜕变 | 3/5/7/10 | 变身、召唤、诅咒、人格/姿态切换 | 三次质变，满套完成形态 |
| 领域仪式 | 2/5/8/10 | 光环、地形、天气、梦境、时间 | 建立领域→扩大→控制→统治 |
| 堡垒联防 | 4/6/8/10 | 重甲、守护、伤害分担、阵型 | 前期门槛较高，形成后稳定增强 |
| 节奏诡术 | 2/3/6/9/10 | 潜行、忍术、位移、预见、重掷 | 早启动、长蓄势、最后一件收束 |
| 顶点高魔 | 3/6/9/10 | 创世、虚空、宇宙、命运等高阶权能 | 少而重的阶段跃迁 |

选择门槛的理由必须来自该套的玩法循环，而不是为了让表格整齐。每套使用 4 或 5 个门槛，避免只做两档，也避免每穿一件都产生难以读懂的小触发。

## 3. 每套奖励链的职责

无论采用哪种门槛，奖励链应覆盖以下四个职责：

| 阶段 | 职责 | 禁止做法 |
|---|---|---|
| 启动 | 给出可感知的主题入口或构筑方向 | 只堆与主题无关的 HP/AC |
| 成形 | 建立可重复的战斗循环，明确触发事实 | 用叙述文本代替触发、目标和频率 |
| 强化 | 扩大循环、补足代价或增加战术选择 | 同一几率/骰子无声明地重复叠加 |
| 10 件封顶 | 完成专属身份、主动技或规则改写 | 仅把前档 `+1` 改成 `+2` |

旧的招牌能力原则上放在成形、强化或封顶阶段。低门槛先让玩家看到主题，满套则让整套 10 件的机会成本获得明确回报。

## 4. 成员识别与计数合同

未来正式定义必须由套装侧持有显式 `member_item_ids[10]`，而不是修改 `ItemDef`，也不能只按 tag 猜成员：

```text
GearSetDefinition
  set_id
  member_item_ids[10]       # 以旧文档的 10 个 item_id 为唯一成员清单
  threshold_definitions[]   # 4 或 5 档，最后一档 required_count = 10
```

计数规则：

- 只统计清单内当前有效装备实例；同一实例最多贡献 1 件；
- 十个既有槽位都可以贡献，`ring_1` 与 `ring_2` 分别按各自成员 ID 判断；
- 损坏失效、卸下、战斗内合法换装时立即重算派生来源；
- tag 只用于检索和审计，不是正式身份主键；
- Set 11 与 Set 95 的身份碰撞解决前，两套都只能保持 planned，不能靠显示名或槽位猜测注册。

## 5. 累计、替换与共享次数

所有逐套条目遵守以下默认规则，只有条目明确声明时才例外：

1. 已达成门槛全部生效；不同门槛的独立静态奖励按来源累计。
2. 同一概念只是在提高骰子、几率、半径、目标数、层数、持续时间或每日次数时，使用同一 `replacement_group`，只取最高档，不把各档相加。
3. 同名主动能力的升级档共享一个 `usage_pool_id`；解锁高档不会把低档已消耗次数重置。
4. 单件特殊效果仍是独立来源，不因套装门槛出现相似效果而消失。若两者确属同一能力，逐套文档必须写明是独立相加、替换升级，还是共享次数。
5. 抗性只使用 `immune > half > normal > double` 的离散层级，同类型重复 `half` 不继续减半。
6. preview 与 AI 只读取派生状态，不消耗次数、不掷真实随机、不写回战斗或世界状态。

## 6. 触发与伤害纪律

逐套文档必须把叙述落成可判定事实：触发时点、来源、目标、范围、持续时间、冷却/次数、状态与清理时点缺一不可。

附加伤害采用龙鳞套确立的伤害段合同：

- 只查询带明确 `DamageOriginKind` 的真实主直接伤害 segment；
- 多段技能逐段判定，不按 cast、skill、目标或 event batch 去重；
- `extra_damage_segments`、装备能力生成伤害、反射、自伤、地形与 timeline tick 不递归触发；
- “命中”与“造成真实 HP 伤害”是不同事实，吸血、击杀和受伤反应必须选择正确事实；
- 同一事件中的 reaction 顺序、致死拦截、复活和伤害改写必须使用明确优先级，不能依赖资源加载顺序。

## 7. 统一记号与 typed owner

| 设计记号 | 正式 owner / 约束 |
|---|---|
| `attr(x,+N)` | 当前 `ItemDef.attribute_modifiers` / 派生套装 modifier 来源 |
| `res(tag,half/immune/double)` | `TraitDef.damage_resistance_entries` 与 canonical damage tag |
| `save(ability,+N)` / `save_tag(x,+N)` | ability save / 状态 tag save query |
| `check(id,+N)` | typed utility-check query；当前仍缺通用 runtime |
| `move(+N)` | `BattleStatusEffectState.move_point_capacity_delta` 派生来源 |
| `hit(filter,+N)` / `save_dc(filter,+N)` | attack-check / outgoing save-DC query |
| `extra(segment,XdY,tag)` | 每主直接伤害段查询，带 origin 与递归排除 |
| `range/radius/move(N 格)` | 当前战斗网格单位；旧文档的尺数不得进入正式 definition |
| `ap_cost(N)` | 主动能力明确消耗 1/2/3 AP；不用 action/bonus action 充当资源单位 |
| `usage(scope,N)` | `per_turn`、`per_battle`、`per_rest`、`per_world_day` 等显式 scope |
| `duration(N TU)` | 战斗时间统一以 TU 表示；回合叙述必须同时给出当前换算后的 TU |
| `state(schema)` | source-bound typed state，规定创建、刷新、消费、清理和存档策略 |

opaque `special_effect_id` 可以作为内容标识，但不能替代正式的 fact、condition、action、roll gate、state schema 与 usage 定义。
`reaction` 只表示结算时序，默认不消耗 AP；若某个反应还需资源，必须单列其正式资源成本。

## 9. 当前实现状态与阻断项

当前仓库已经具备通用 `GearSetDefinition`、成员注册、累计门槛 evaluator 与派生套装来源；凤凰重生已经完成装备能力、AI/preview、展示、存档与唯一获取链。其余套装仍须逐套核对，不能沿用 Set 53 的落地结论。

| 项目 | 状态 | 影响 |
|---|---|---|
| 100 套逐套奖励链 | mixed | Set 53 已落地；其余逐套方案仍是后续资源与测试输入 |
| 10 成员显式计数 | framework implemented | Set 53 已由真实十成员与 3/5/7/10 阈值回归验证；其余套装仍需逐套注册与验证 |
| 属性 / Trait / 装备能力投影 | mixed | 通用 owner 已存在且 Set 53 已接入；其余方案不能据此视为已实现 |
| preview、AI、UI、存档 | Set 53 implemented / others planned | Set 53 有正式跨路径回归；其他套装仍不能以加载成功代替行为验证 |
| Set 11 / Set 95 共用 `star_weaver_set` 且四个 ID 碰撞 | P0 blocker | 未获配置消歧授权前不可注册 |
| 21 套护甲/饰品标题漂移 | audit warning | 不影响显式 ID 计数；本轮不改名，UI 正式标签仍需单独决策 |
| Set 100 单件全伤害免疫 | balance blocker | 单品冻结条件下无法证明整套强度闭合；套装奖励避免继续叠防御 |

## 10. 后续落地验收

正式实现至少要证明：

1. 100 套各有且只有 10 个既有成员，所有成员都能贡献计数；
2. 每套有 4 或 5 个递增门槛，最后一档严格为 10；
3. 单件配置零漂移，旧招牌机制在新奖励链中有可追踪去向；
4. 累计、替换、共享次数和清理规则有 focused regressions；
5. 换装、损坏、双戒指、preview、AI、UI、保存/读取都使用同一份 canonical snapshot；
6. 每段伤害、递归排除、致死顺序和 usage 消耗测试能在实现回归时真实失败；
7. Set 11/95 与 Set 100 的阻断项必须单独解决，不能用兼容别名或隐藏 nerf 绕过用户的配置冻结要求。
