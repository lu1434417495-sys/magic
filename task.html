内容 JSON 迁移 · 分步任务书

历史实施方案：docs/archive/implementation-plans/landed/2026-08-23-content-json-direct-load.md（v1.4）；当前实现真相见 docs/design/foundations/content_json_authoring.md。

如何使用

任务按 ID 顺序执行。每个任务是一次独立会话的工作量，完成后提交一次。标注「闸门」的地方必须停下，把结果报告给用户后再继续，不要自行判定通过并推进。

每个任务卡包含：依赖、目标、范围、步骤、验收、陷阱。陷阱一栏是本仓库已经踩过的坑，不是泛泛提醒，请逐条确认。

全局约束

  1. 日志禁止 GD.Print。一律使用 GameLog 或 ConsoleProcessOutput，临时探针也不例外。仓库有静态检查会拦。
  2. 禁止用 git checkout 回退文件。工作树中常有其它未提交的并行改动，会被一起抹掉。需要回退时用文件移动或手工反向编辑。
  3. 读 res:// 下的文件必须走 Godot FileAccess，禁止 System.IO。后者在编辑器里能跑、在导出包里读不到（内容在 .pck 内）。同理目录用 DirAccess，且不要先经 ProjectSettings.GlobalizePath——该方法对 res:// 在导出项目中无效。
  4. .tres 中的 Array<T> 导出属性必须显式写出，空数组也要写成 Array[ExtResource("x")]([]) 并保留对应 [ext_resource] 脚本引用。整个省略会在 GC 阶段 gchandle.is_released() fatal（exit 3221225501），报错栈全在引擎内部、不指向任何文件。
  5. 不要为了整洁删除 Resource 子类上的 [Export] 属性，即使全仓无 .tres 引用它。实测会让内容校验回归在 finalizer 阶段约 80% 概率崩。要禁止某个取值就在 validator 层 fail-closed，字段留着。
  6. 内容校验回归的崩溃要跑 5 次统计通过率。这类崩溃单跑可能通过、成组才崩，且 --jobs 1 同样崩——不是并行写入问题，别往那个方向排查。
  7. 不加兼容层。禁止旧 schema 别名、静默 fallback、双查找、legacy 字段支持。仓库政策要求先与用户确认，本方案已明确不做。
  8. 不在迁移提交里顺手改数值。机械转换与内容调整分开提交。
  9. 基础六项属性不允许被扣减。若某任务看起来需要写入基础属性，先停下确认——引擎只读不写是规则，不是缺口。
  10. 代码改动后按需更新 docs/design/project_context_units.md；提交信息用 Conventional Commits（feat: / fix: / refactor: / docs:）。

常用命令

dotnet build magic.csproj
python tests/run_regression_suite.py
godot --headless -s res://tests/<domain>/<runner>.cs

全量回归请前台分块跑。放后台约两分钟就会误报「完成」。战斗模拟与平衡 runner 不属于常规全量，除非任务明确要求，否则不要带上。

P1修复 res:// 目录发现守卫

依赖：无 · 预计：小

目标
让内容目录发现在导出包中可用。当前写法只在编辑器下成立。
范围
scripts/ 下所有 DirExistsAbsolute 调用点（约 14 处、16 个文件），含 Skill / Item / Recipe / Enemy / Quest / Profession / Progression / GearSet / Barrier / BattleEncounter / SpecialProfile / ContingencyTemplate / Identity 等 registry。
步骤
  1. 先确认问题：ProjectSettings.GlobalizePath("res://…") 在导出项目中不适用，会得到可执行文件目录下一个不存在的原生路径，导致守卫返回 false、发现逻辑直接返回、内容一个都不加载。
  2. grep 出全部调用点，逐个检查路径协议。
  3. 只改 res:// 的站点：去掉 GlobalizePath，直接以 res:// 路径判存在，或删掉预检查、依赖 DirAccess.Open 返回 null 的既有分支。
  4. 保留原有校验错误文案，除非某条消息因此不可达。
验收
全量回归通过；scripts/ 下不再有对 res:// 路径调用 GlobalizePath 后判存在的写法。
陷阱
FileIOCoordinator.cs 与 GameSession.SaveIndexAndFileIO.cs 也匹配同一模式，但它们操作 user://——GlobalizePath 对 user:// 是有效的，不要改。AiTraceRecorder.cs 写非 res 路径，同样先确认再动。

阶段 0 · 跨域基础设施

本阶段不碰任何业务内容，只建地基。作者工具（T0.7 / T0.8）是一等交付，不是收尾项——LLM 生成的可行性取决于它们。

T0.1JSON 文档加载器与 IO 分层

依赖：无 · 参考：设计文档 5.1.1、5.2

目标
建立文件发现与 UTF-8 读取，并把 Godot 依赖压缩到单一薄层。
范围
新建 scripts/systems/content/json/ContentJsonDocumentLoader.cs。
步骤
  1. IO 层：FileAccess 读字节、DirAccess 发现文件，只有一个方法，可被测试替身注入。
  2. 文档层：解析 envelope（schema / domain / family / templates / entries），拒绝未知根字段。
  3. 诊断：source label 格式 file.json#entry_id，附 JSON pointer。source label 只用于诊断，不得进入 import model、Definition、snapshot 或存档。
  4. 重复 entry ID 聚合报告，不是遇到第一个就抛。
验收
UTF-8、schema/domain 校验、未知根字段、重复 entry ID 四类文档测试通过；解析层以下的测试不依赖 Godot。
陷阱
不要用 System.IO（全局约束 3）。JsonDocument 在单文件解析结束时释放，JsonNode 不得逃出解析调用栈。

T0.2文件内 template 合并器

依赖：T0.1 · 参考：设计文档 6.2

目标
实现文件内模板合并，仅此一种去重手段。
范围
新建 scripts/systems/content/json/ContentJsonTemplateMerger.cs。
步骤
按设计文档 6.2 的合并表实现：对象递归合并、数组整体替换、标量显式覆盖（0/false/空串都是有效值）、键缺失保留模板值、null 仅用于 schema 声明可空的字段、多级 template 允许链式继承但必须检测环与未知模板。
验收
对象合并、数组替换、显式零值、null、环、未知 template 六类测试通过。
陷阱
不实现数组 append/remove/merge-by 指令、跨文件 template、template import、条件模板或对象共享引用。这些都是明确禁止项，加上去会让 schema 无法闭合。

T0.3共享 canonical JSON writer

依赖：T0.1 · 参考：设计文档 11.2

目标
一个 writer 同时服务 parity 比较、Definition golden 和转换器实际产出。
范围
新建 scripts/systems/content/json/ContentCanonicalJsonWriter.cs。
步骤
  1. 输出必须直接是目标 schema 的合法文档，不是「用于比较的调试表示」。
  2. 对象键按 schema 声明顺序输出（不按字母序，保证产出文件可读）；数组保持源顺序。
  3. 浮点用可逆表示，不截固定小数。
  4. enum / value object 输出稳定业务字符串。
  5. 省略等于 DTO 默认值的字段。
  6. 不输出 source label、文件路径、UID 或任何诊断字段。
  7. parity 比较使用键序无关比较；文件产出使用声明顺序。这是同一 writer 的两种消费方式，不要写成两个 writer。
验收
writer 往返测试：任意 import model → JSON → import model 逐字段一致；浮点边界值可逆。
陷阱
「省略默认值」与「键缺失继承模板值」会相互作用。writer 阶段没有 template 所以安全，但要在代码注释里写明这个前提，后续 template 提取任务依赖它。

T0.4domain descriptor 与 import batch 契约

依赖：T0.1 · 参考：设计文档 5.2、5.2.1、5.2.2

目标
定义单域链路的注册形态，并明确它不负责跨域顺序。
范围
新建 JsonContentDomainDescriptor.cs、ContentImportBatch.cs。
步骤
  1. descriptor 只拥有：source discovery → 文档加载 → template 合并 → DTO 解析 → import model → domain-local 校验。
  2. 跨域构建顺序保留在 ContentSnapshotBuilder 的现有显式编排中。不要写通用拓扑排序。
  3. 需要外域输入的校验与投影保留现有显式签名，由 builder 传参。
  4. import batch 携带聚合诊断，不是遇错即抛。
验收
descriptor 可注册一个空的示例 domain 并跑通空链路；ContentSnapshotBuilder 的既有依赖顺序未被改动。
陷阱
现有 builder 是显式依赖图，不是 domain 循环：recipe 依赖 item，special profile 依赖 skill，enemy 依赖 item+skill，encounter 依赖 enemy roster/template，且有一部分 item 由技能合成、没有 source 文件。任何「每域一个 descriptor 就够了」的设计都会在后续阶段撞墙。

T0.5引擎资产 catalog 与 ID resolver

依赖：无 · 参考：设计文档 8.1–8.3

目标
建立 asset ID 到 typed Godot 资源的解析边界。这是唯一保留 Resource authoring 的地方。
范围
新建 EngineAssetCatalogDef.cs、四个 typed entry Def、EngineAssetCatalogBootstrap；扩展 EngineAssetResolver.cs。
步骤
  1. catalog root 分别导出 Array<EngineTextureAssetEntryDef>、Array<EngineSceneAssetEntryDef>、Array<EngineAudioAssetEntryDef>、Array<EngineShaderAssetEntryDef>。不要用 polymorphic Array<Resource>。
  2. 每类 entry 只含稳定 asset_id 与对应明确类型的 Resource 属性。
  3. resolver 构建 asset_id → borrowed typed Resource 只读索引；asset ID 重复、目标缺失、类型不符必须报错。
  4. catalog root 由现有 process engine-asset 生命周期拥有；quiesce 后拒绝新 path load 但保持已发布 snapshot 的 ID 查询合同。
验收
asset ID 唯一性、同一底层资产不登记多个 ID、类型不符报错、optional 空值、quiesce/shutdown 五类测试通过。跑完整回归分组，并重复 5 次统计通过率。
陷阱
这是全局约束 4 和 5 的高发区。四个数组里初期很可能有一两个为空——空数组必须显式写出并保留 ext_resource 绑定，否则 gchandle.is_released() fatal，且报错不指向任何文件。单跑通过不算数。

T0.6拆分 resolver API：内容 ID 与代码路径

依赖：T0.5 · 参考：设计文档 8.3

目标
让「内容给的 ID」和「代码自己拥有的路径」在类型与命名上无法混用。
步骤
提供 ResolveContentAssetBorrowed<T>(StringName assetId) 与 ResolveCodeAssetBorrowed<T>(string codeOwnedPath) 两个分名入口；后者只允许代码自身拥有的场景、shader 或 bootstrap 常量使用。
验收
内容字段无法传入 code-path API（编译期或运行期均可，但必须有测试覆盖）。
陷阱
现有 EngineAssetResolver.ResolveBorrowed<T>(string resourcePath) 是路径入口，改造时不要一刀切改签名——先确认现有调用方各属哪一类。

T0.7JSON Schema 导出器

依赖：T0.4 · 参考：设计文档 11.7 · 生成能力的前提

目标
从代码侧 DTO 与 closed kind spec 生成 JSON Schema，作为作者与生成方的唯一契约来源。
步骤
  1. 由 DTO 反射生成，禁止手写 schema——手写必然与 DTO 发散。
  2. 每个 domain 一份，随 DTO 变更重新生成并纳入版本控制。
  3. 覆盖字段名、必填、枚举取值、按 kind 的 payload 形状。
  4. 内容文件不引用 schema 文件路径（违反路径禁令）；编辑器侧靠工作区配置做 glob 关联。
验收
导出的 schema 与 DTO 同步的测试；schema 变化能被 CI 检出。
陷阱
因为 DTO 用 JsonUnmappedMemberHandling.Disallow，schema 必须完整准确，否则生成方会被合法字段挡住。schema 描述不足是后续误报的主因，宁可写详细。

T0.8离线校验 CLI

依赖：T0.1–T0.4、T0.7 · 参考：设计文档 11.7 · 生成能力的前提

目标
不启动游戏即可校验内容文件，秒级反馈。
步骤
  1. 只跑「文档解析 → template 合并 → DTO strict parse → domain-local 校验」。
  2. 输入可以是单文件或整域。
  3. 诊断输出 file.json#entry_id + JSON pointer + 稳定规则标识，格式与运行时诊断一致，且必须机器可读（后续要作为生成方的修复输入）。
  4. 跨域校验不由 CLI 承担，也不要假装能承担——那需要完整 snapshot。
验收
对故意构造的错误文件产出可定位到字段的诊断；诊断格式有测试锁定（后续生成闭环依赖它稳定）。
陷阱
诊断文本会成为机器接口。一旦生成闭环接上，随意改文案就是破坏接口——所以要用稳定规则标识而不是靠匹配文案。

T0.9Windows 导出 preset 与 smoke runner

依赖：T0.5 · 参考：设计文档 12.4 · 绿地基建

目标
建立受版本控制的导出配置，并证明 asset catalog 能在真实导出包中加载。
步骤
  1. 新增 export_presets.cfg，至少一个 Windows Desktop smoke preset。
  2. 确认 .json 的打包机制：项目内 png/jpg/csv/svg/fbx/glb 都有 .import，.json 一个都没有，说明它是非资源文件、不会像 .tres 那样自动打包，需要非资源文件过滤显式包含。把结论写进 preset 注释。
  3. smoke runner：从导出产物启动，缺文件 / 缺 catalog entry / 类型错误导致非零退出。
  4. 导出产物写临时目录，不提交二进制包。
验收
DG-0 只卡最小项：导出包能启动，且 typed asset catalog root 与其引用资产被正确打包。构建完整 ContentSnapshot 的完整 smoke 属于各域完成定义，不是本任务的验收线。

这是本仓库第一次真正导出（此前无 preset、scripts/ 下无任何 editor/template 分支）。很可能撞上一批与 JSON 无关的既有导出断裂（P1 是已知的一个，未必是唯一一个）。这部分排障时间单独记，不要算进 JSON 迁移工作量，也不要因此判定方案有问题。遇到超出本任务范围的断裂，记录下来并向用户报告，不要顺手扩大改动。

闸门 DG-0 — 停下并报告

同时满足才进入域迁移：纯基础设施测试通过；asset catalog 的 process owner 行为正确（含 5 次通过率统计）；导出最小项通过；不存在任何 JSON authoring Resource 或通用反射 binder。

完整导出 smoke 不是 DG-0 前置。若导出基建未就绪但最小项通过，可以开始 T1a，但不得进入阶段 2。

T1a.6转换器接入与 7 个虹彩屏障 round-trip

依赖：T0.3、T1a.4 · 参考：设计文档 11.1、11.3、11.6

目标
打通 .tres → TresAdapter → ImportModel → canonical writer → .json，并证明闭合。
步骤
  1. 转换器是 headless Godot 入口（读 .tres 需要 Godot 资源系统），不得自己解析 .tres 文本。
  2. 转换器 = TresAdapter + canonical writer 的组合，没有第三段逻辑。
  3. 按 domain 调用；默认写临时目录，--in-place 才写 data/；任一 entry 失败即整域非零退出，不产出部分结果。
  4. round-trip 断言：canonical(tres→ImportModel) == canonical(转换器json→ImportModel)，对 7 个 prismatic ward 逐 entry 执行。
验收

T1a.7技能 validator 的 diagnostic golden 语料

依赖：无（可与 T1a.1–6 并行）· 参考：设计文档 12.2 · 整条链上最关键的一步

目标
在重构之前固化 validator 的现有诊断行为。本任务只记录，不改 validator。
步骤
  1. 正例语料：用当前 validator 对全量真实内容跑一遍，记录诊断输出（正常应为空，空也要固定下来）。
  2. 反例语料：为 validator 中每一条规则分支构造至少一个触发用例，记录其诊断，形成受版本控制的 fixture 集。
  3. 规则清点：反例逐条对应规则分支，缺一条即视为语料未完成。
  4. 语料建立在 .tres 侧（当前唯一 source）。
验收
规则分支与反例用例的对应表完整；语料可重复执行并产出稳定结果。
陷阱
SkillCombatProfileValidator.cs 是三千行量级，规则分散。若某条规则无法构造反例，说明它是死规则——单独提交删除，不要带着搬走。这条语料是后续唯一能发现「重构静默丢规则」的手段；双层 parity 对此在构造上不可见（两侧共用同一 validator）。在 LLM 生成量级下，丢一条规则会放大成上千条错误内容。

停止条件

触发任意一条时停止扩大范围并向用户报告，不要用临时兼容层继续推进：

  1. 需要在 JSON 里写路径、类型名或通用引用语法才能继续；
  2. 需要 pathless Resource 才能复用现有 validator；
  3. 无法让 .tres 与 JSON 汇合到同一 import model；
  4. 转换器在某域无法达成 round-trip 全量闭合，且原因是 authoring 语义本身无法用 JSON 表达；
  5. diagnostic golden 语料无法覆盖某个 validator 的规则分支；
  6. domain kind 只能靠字段形状或 ID 文本猜测；
  7. Windows 实际导出无法证明 JSON / catalog / 依赖完整；
  8. world 阶段仍需要路径兼容、别名或静默 fallback；
  9. 发现 Resource adapter 与 JSON importer 形成了两套业务投影。
